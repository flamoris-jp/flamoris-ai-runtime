# Security Policy

FLAMORIS AI Runtime is currently a design-stage project.

Security boundaries are part of the architecture, especially because the intended workflow author may itself be an AI.

## Core security assumption

**Workflow JSON is untrusted input.**

A workflow request must not gain authority merely because it was generated by a trusted-looking model or Agent.

## Planned security boundaries

The runtime design should enforce:

- schema validation;
- allowlisted node types;
- explicit capability registration;
- caller authorization;
- bounded resource use;
- bounded concurrency and fan-out;
- explicit side-effect classification;
- cancellation and timeout policy;
- stable redacted errors;
- no embedded secrets in workflow JSON;
- no ambient shell/filesystem/network authority.

## Secrets

Never commit or publish:

- API keys;
- access tokens;
- passwords;
- private keys;
- production credentials;
- private deployment topology;
- sensitive user data.

Workflow examples must use placeholders or abstract credential references only.

## Arbitrary code execution

General shell, Python, or arbitrary code execution is not part of the initial runtime design.

Any future code-execution capability would require an explicit sandbox, permission model, resource limits, and threat model. It must not be introduced as an ordinary convenience node.

## External services

Responses from models, tools, MCP services, HTTP services, files, and retrieved knowledge must be treated as untrusted data.

Do not allow upstream output to redefine runtime policy or caller permissions.

## Reporting a vulnerability

Use GitHub private vulnerability reporting when available for this repository or contact the maintainers through an appropriate private channel.

Do not publish secrets or sensitive exploit details in a public Issue.

FLAMORIS software is provided as-is and does not include a guaranteed response-time commitment.
